# Release v1.1.0 — NPU support, and NPU training that tells the truth

NPUs are now detected across vendors, the runtimes that drive them are enumerated, and a training run
can hand an NPU the work it can actually finish. What it cannot do is stated in the same breath.

## What shipped

### Detection is vendor-neutral

`utils/hardware/npu.py` used to know one vendor. It now reports a matrix, with the AMD path kept
byte-for-byte compatible so existing NPU inference keeps working:

| Vendor | Match | Family |
| --- | --- | --- |
| AMD | `1022:17f0` supported, `1022:1502` present but unsupported | XDNA2 / XDNA1 |
| Intel | `8086` with `7d5d`, `ad1d`, `643e`, `b03e`, plus any `8086` device whose PCI class is `0x118000` | NPU3 / NPU4 / NPU |
| Qualcomm | `17cb` with `1100`/`1101`, plus any `17cb` accelerator-class device | Hexagon |
| Apple | Apple Silicon, `hw.optional.ane` | ANE |
| Microsoft | No PCI id; hosts the Windows ML provider | — |

An unlisted Intel or Qualcomm device that presents itself as a processing accelerator (PCI class
`0x118000`) is still reported as present, with `supported: false` — claiming runtime support for a
generation with no known id would be a claim, not a measurement. That class fallback is Linux-only, and
unlisted AMD ids are not reported at all, because their driver does not expose the class the others do.

Detection stays behind `UNSLOTH_STUDIO_ENABLE_NPU=1`, matching the NPU inference gate.

### The runtime matrix

`utils/hardware/npu_providers.py` enumerates every runtime an NPU could use and what each can serve:
OpenVINO, ONNX Runtime QNN, Vitis AI, FastFlowLM, Lemonade, Windows ML. Every row is always returned;
the installed ones are marked. A version is reported where the thing has one to report — a bare
executable (FastFlowLM, Lemonade) and the Windows ML projection do not. Nothing is imported to answer — packages, modules and
executables are probed, and every probe is individually guarded so one wedged runtime cannot blank the
others.

### What the NPU can do for a training run

`core/training/npu_assist.py` plans the run's arrangement rather than labelling it:

| Task | What the NPU runs |
| --- | --- |
| `tokenize` | Reading and tokenizing the dataset |
| `eval` | Scoring checkpoints while training runs |
| `qat_calibrate` | Calibrating quantized weights |

The backward pass stays on the primary compute device, and the plan says so in a sentence. No vendor
exposes a backward pass to PyTorch today, so `requested="full"` is answered with
`refused_reason="no_backward_pass"` — the mode exists so a refusal can be *explained* instead of an
explicit request being silently downgraded. The card offers assist and off today; `full` is reachable
through the route. When a provider row claims a backward pass, the same code path returns
`mode: "full"` with no other change — the claim lives in one table, not in the planner.

The offload queue behind it is bounded, single-consumer and lossy: a full queue drops the submission
and the training step keeps the time it had. A training step that waits on a queue is a slower
training step.

### In the Studio

- `GET /api/compute/npu/assist` answers the plan preview — enabled, mode, tasks, providers, refusal
  reason, and the sentences the UI shows verbatim.
- The Train wizard shows an "NPU acceleration for training" card beside the device picker: what the NPU
  will take over, what will serve it, and the two buttons that ask for it or leave it off.
- An NPU that is present but unusable keeps its row in the picker with the reason attached, instead of
  disappearing.

## Limits, stated

- **No NPU can train a model.** This release does not change that, and does not pretend to.
- The assist queue is not wired into a live training loop behind a provider that can act on the
  payloads yet: the planner, the queue, the capability report and the UI are here, and the tokenizer
  and evaluator adapters land when a provider is installed to drive them.
- `mode: "full"` is unreachable by construction until a provider claims a backward pass.
