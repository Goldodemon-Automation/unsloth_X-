# Release v1.4.1 — Intel is seen, and the installer carries its backend

Two things at once: the installed app stops carrying a backend that was built somewhere else, and the
machine probe stops missing the Intel hardware it is running on. The rest is the opt-in telemetry
surface and the CPU fallback that keeps a run alive when torch cannot open an accelerator.

## Installers

Four installers, one behaviour; all four now carry the fork backend wheel. They still differ only in
the environment the desktop shell hands to its first-run installer:

| Asset | What it pins |
| --- | --- |
| `Unsloth_1.4.1_x64-cpu-gpu-setup.exe` | nothing: probes the machine and installs what it can run. **Use this one.** |
| `Unsloth_1.4.1_x64-gpu-setup.exe` | nothing: CUDA on NVIDIA, Vulkan on an Intel/AMD iGPU; torch follows the driver |
| `Unsloth_1.4.1_x64-cpu-setup.exe` | CPU-only torch index and CPU llama.cpp, no GPU probe |
| `Unsloth_1.4.1_x64-cpu-npu-setup.exe` | CPU stack, with `UNSLOTH_STUDIO_ENABLE_NPU=1` set at launch |

Every `.exe` carries a `.sig`, and `latest.json` is the manifest the in-app updater reads. They use the
same updater key introduced in `v1.4.0`, so existing installs can update normally.

The `-npu` build still differs from the CPU flavor in exactly one way: the NPU gate is already open.
The NPU is driven by Lemonade/FastFlowLM, which the Studio installs on first use. Detection is not a
runtime, and no installer changes the NPU's real limit: inference and assist only, because no vendor
exposes a backward pass.

## The backend now matches the shell

The `v1.4.0` installer asked PyPI for `unsloth`, while the desktop shell's Labs, merge and telemetry
routes live only in this fork. On a machine where PyPI served a backend without those routes, the UI
got 404s and 405s for endpoints the shell was already calling. The backend was not broken; it was the
wrong backend.

The release workflow now builds a wheel from the same commit in a `backend` job before any installer
leg starts. Tauri bundles it as `backend-wheel`; `install.ps1` finds it beside the app and installs it
with `uv pip install --reinstall-package unsloth --no-deps`. That replaces only `unsloth` and keeps the
torch family the installer selected, including the Intel XPU stack. A standalone install with no
bundled wheel still resolves `unsloth` from PyPI as before.

The installed `1.4.1` app now reports `unsloth 2026.10.6` and serves the routes the shell was built
for: `/api/labs`, `/api/advanced/capabilities`, `/api/advanced/outputs` and
`/api/advanced/merge/history` all return 200. Sending an empty merge request returns 400 with
`Every merge slot needs a model.` — a validation error, not a missing route. No new 404 or 405 has
appeared since the installed app launched.

## The machine is seen: Intel NPU and XPU

- **Core Ultra 200H NPU.** The Intel device table now includes `fd3e` as `NPU3`, the NPU in Arrow
  Lake-H / Core Ultra 200H machines. It sits beside the existing Meteor Lake, Arrow Lake/Lunar Lake,
  Panther Lake and Keem Bay entries.
- **Plain `Intel(R) Graphics` is XPU-capable.** Core Ultra's integrated GPU can report that exact name
  rather than an Arc or Data Center GPU name. The XPU classifier now accepts it, so the Intel wheel
  path is no longer skipped on those machines.
- **A real NVIDIA driver still wins.** Plain `Intel(R) Graphics` is accepted for the Intel path but is
  not treated as proof that XPU works. `Test-IntelXpuRuntimeProven` keeps it out of the NVIDIA
  override decision unless PyTorch has actually proven XPU, so a hybrid machine with a discrete
  NVIDIA card keeps the NVIDIA path.
- **The GPU installer auto-detects CUDA or Vulkan.** The `-gpu` flavor no longer pins llama.cpp to
  CUDA. Both the GPU and universal flavors leave the pin empty so the host chooses CUDA on NVIDIA or
  Vulkan on a supported Intel/AMD iGPU. The CPU and NPU flavors still pin the CPU stack.
- **CPU CoRA when torch cannot open its accelerator.** The CPU-training verdict now covers
  `no_gpu`, `torch_cpu_build` and `torch_cuda_unavailable`. A machine with a CPU-only torch build, or
  one where torch cannot open its GPU, can use CoRA's transformers + PEFT path instead of being gated
  out of training. Intel Macs remain gated.

## Telemetry is opt-in, and it shows its payload

**Settings → Telemetry** is the whole surface. Collection is off until the installation owner turns
it on; the tab renders the exact JSON payload before anything leaves the machine, and **Send now** is
the same send on demand. The default interval is six hours.

The standalone collector and operator dashboard live in `telemetry/`. The app is not configured to
send anywhere until an endpoint is set. Reports are stored per install and per day: token counts by
chat and OpenAI-compatible API, model ids and response counts, training runs, merges, hardware
classes, app/Python/torch/transformers versions, locale and feature counters. Prompts, replies, chat
titles, file or folder paths, hostnames, usernames, email addresses, Hugging Face tokens, API keys and
IP addresses are never stored. The install id is a random UUID, not a hardware or account
identifier, and a report replaces the day rows it covers so retries are idempotent.

The settings routes are owner-only, and mutations require an interactive UI session; an API key
cannot turn reporting on or push a report by hand.

## Limits and one Windows note

- **The NPU runtime is not bundled.** The NPU can be detected on Core Ultra, but Lemonade/FastFlowLM
  is installed on first use. On the verification machine the NPU is present and
  `runtime_installed=false`, so detection is not the same as a ready inference runtime.
- **NPU training is still impossible.** The runtime pair has no backward pass to drive; NPU remains
  inference and assist.
- **First capability probe is slow.** The cold XPU path can spend most of a minute warming torch
  before the merge capability list appears. Later calls are fast.
- **Some endpoint protection flags the first-run script.** The application binaries are signed; the
  first-run PowerShell script is not. If a product such as McAfee blocks it with a
  `ScriptContainedMaliciousContent` finding, add a narrow exclusion for the app folder or submit the
  script as a false positive. Do not turn off real-time protection globally.
