# Release v1.2.0 — the UI pass

The device work from v1.0.0 and v1.1.0 is only useful if the Studio explains it, and a claim that a
UI got faster is only worth making if it can be measured. This release is the second half of both: a
card that answers "what can this machine do" in plain words, and an instrumentation layer that
answers "did that change help" with numbers instead of an opinion.

## What shipped

### The device decision, in the Train wizard

The capacity card now leads with **Run on**: one row per device, each with its memory, its kind
(CPU / GPU / Integrated GPU / NPU) and — for a device it cannot use — the reason in plain words
instead of a silent grey. Unsupported devices stay listed on purpose: "this machine has an NPU that
cannot train" is different information from "this machine has no NPU".

The capacity check below it sizes the run for the **selected** device, sends `compute_target` with
the request, and surfaces the budget module's own sentence — *"This GPU shares system memory: 38.4 GB
of the machine's 64.0 GB is usable for training, 60% of it."* A bare `0.5 GB` beside a 3 GB model
reads as a refusal on a 16 GB laptop unless it also says the card shares that RAM.

### "What can this machine do?"

One click under the picker: the resolved device, its recommended precision, whether 4-bit is
available, the budget sentence in full, and a supported/unsupported mark per device. Every reason
token (`arch_unknown`, `no_backward_pass`, `torch_missing`, …) is mapped to a sentence in one
function, because a user reading `no_backward_pass` learns nothing.

### The NPU card

Beside the picker: what the NPU will take over, what will serve it, and two buttons — "Use the NPU
where it helps" / "Leave it off". A refusal names its reason, and only the `no_backward_pass` refusal
adds the sentence that matters: NPU-only training becomes possible when a vendor ships a backward
pass. The mode is offered so the answer can be explained, not so the request can be quietly
downgraded.

### A perf layer, so the next change can be measured

`src/lib/perf/` — dependency-free, inert unless enabled, and cheap enough to leave in a production
bundle:

- `perfEnabled()` turns instrumentation on with `globalThis.__UNSLOTH_PERF__ = true`,
  `VITE_UNSLOTH_PERF=1`, or `?perf=1`. Off, every call is a no-op: `measure` returns `null`, `mark`
  touches nothing, `time`/`timeAsync` are exactly the wrapped call.
- `mark` / `measure` / `time` / `timeAsync` write User Timing entries and a bounded ring
  (`MAX_ENTRIES = 200`). `measure` consumes its marks, because the performance timeline retains them
  until cleared — that is the leak the bound exists to prevent.
- `observeLongTasks()` wraps `PerformanceObserver` and is inert where the entry type is unsupported
  (Safari, Firefox). It keeps numbers and an attribution string, never the entry objects.
- `trackInteraction(name)` measures to a double-`requestAnimationFrame` boundary and records through
  `measure`, so a slow click and a slow render land in one place.
- `installPerf()` arms it at startup when enabled; `main.tsx` calls it once.

`reportLines()` returns the lines slowest-first, which is the whole interface: no overlay to build, no
library to configure, the caller decides where to put them.

## Limits, stated

- Nothing here changes how a run trains; it changes what the Studio explains and what it can measure.
- Instrumentation is off unless explicitly enabled: a release build pays one boolean check at startup.
- This release measures the UI; it does not claim a speedup. `docs/ui-performance.md` is how the next
  change gets a number attached to it.
