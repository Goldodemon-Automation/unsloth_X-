# Release v1.0.0 — CPU and integrated-GPU training

The first release on this fork's own series. Training no longer requires a CUDA card: a machine with
no accelerator, or with a GPU that shares its memory with the operating system, now has a first-class
device the Studio can describe, size a run for, and start it on.

## What shipped

### One place that knows the devices

`studio/backend/core/training/device_targets.py` enumerates every candidate — CPU, integrated GPU,
discrete GPU, NPU — with a stable order, an explicit capability set per device, and one rule for the
automatic choice (discrete, then integrated, then CPU; never the NPU, which cannot train).

Before this, the answer was a coarse `DeviceType` plus a global `CHAT_ONLY` flag and a pile of
`DEVICE_TYPE == "cuda"` compares. A host with no accelerator had no way to *name* the device it was
about to train on, and an integrated GPU had no way to say that its memory is shared.

Capability rules that matter, each pinned by a test:

- **No 4-bit on an integrated GPU.** bitsandbytes ships no kernels for an integrated part, so a 4-bit
  load dequantizes on the CPU every step — slower than fp16 and using the memory it was meant to save.
- **No `bf16` on AMD gfx10.** RDNA 1/2 advertise bf16 they cannot run, and Triton's dot then takes the
  process down inside LLVM with no Python exception (issue #7922). Those parts get fp16.
- **Unmeasured is `false`.** A `false` costs a slower path; a wrong `true` kills the run mid-step.

### The integrated-GPU memory budget

`utils/hardware/accelerator_budget.py` defines the one rule for "how much memory can this GPU actually
reach":

```
usable = max(carve-out, system_memory * 0.6)
```

`torch.xpu`/`torch.cuda` report the carve-out on an integrated GPU — often 512 MB — while the driver
allocates well past it out of system RAM. A fit check that trusts `total_memory` refuses models the
machine runs happily; one that ignores the reservation plans against memory the driver will not hand
over. The same module carries the allocator defaults each target needs
(`expandable_segments` on shared memory, the SYCL persistent cache, immediate command lists) and
applies them with `setdefault`, so a value the user typed always wins.

### The target reaches the worker before torch does

`core/training/compute_target_env.py` turns the chosen target into environment for the training
subprocess — the second thing `run_training_process` does, after two `os.environ` writes and before any
torch, SYCL or Unsloth import, because all three read these values at import time.

`unsloth/device_type.py` gains the matching library-level override, `UNSLOTH_TRAINING_DEVICE`, and it
is **opt-in on purpose**: Unsloth's kernels assume an accelerator, and a silent CPU fallback would turn
a broken driver into a run that is 50-100x slower instead of one that refuses. `igpu` resolves to
whichever accelerator backend is actually usable and refuses rather than quietly training on the CPU
when none answers.

### The UI decision, where the decision is made

The Train wizard's capacity card now carries a device picker (CPU / integrated / discrete / NPU, with
memory, capability reasons and keyboard access), and the capacity check sizes the run for the selected
device. A choice is remembered per installation — in the app settings, not the browser — so a job
started from the CLI or another tab runs where the user chose, and `auto` stays `auto`.

A run that asks for 4-bit on an integrated GPU is switched to 16-bit, with the reason in the log: the
capability report says 4-bit is unavailable there, and reporting it without acting on it would let the
request run the slow path and blame the hardware.

The estimate also says where its ceiling came from: *"This GPU shares system memory: 38.4 GB of the
machine's 64.0 GB is usable for training, 60% of it."* A bare `0.5 GB` beside a 3 GB model reads as a
refusal on a 16 GB laptop unless it also says the card shares that RAM.

### API

- `GET /api/compute/targets` — every device, its capability, the recommendation, the budget and the
  resolved choice. Unsupported devices are included on purpose: "this machine has an NPU it cannot
  train on" is different information from "this machine has no NPU".
- `POST /api/compute/target` — validate, remember, answer with what it resolves to. `400` with the
  reason when it cannot.
- `TrainingStartRequest.compute_target` and `/api/train/fit`'s `compute_target` — the request wins,
  then the stored choice, then `auto`.

## Limits, stated

- A CPU run is real but slow: 50-100x a GPU run of the same shape is the order of magnitude the UI
  quotes. It is an estimate, not a measurement of your workload; the setup line names the device so a
  surprise is a small one.
- An integrated GPU's budget competes with the operating system. Expect the real ceiling to be a few
  GB below the number.
- 4-bit training on an integrated part is turned into a 16-bit run at start, not attempted.
- Nothing here changes a discrete-GPU run: the environment and kernels are untouched. The wizard does
  now offer a starting batch size and dtype from the registry's table.
