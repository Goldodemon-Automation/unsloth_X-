# Release v1.3.0 — the CPU run gets tuned, and the device decision gets checked

Five pieces of work, all of them things the previous verification pass said were missing rather than
things nobody had thought of: the CPU training path now uses the machine it lands on, the start path's
rules have tests, the UI survives a failed device probe, the two capability answers agree, and the
polled route is single-flight.

## A CPU run is now tuned for the machine it lands on

A CPU run is 50-100x the wall clock of a GPU run, and most of that gap is decided by settings nobody
sets. `core/training/cpu_tuning.py` decides them from measured facts, and `_load_cpu_model` applies
them:

| Choice | Rule |
| --- | --- |
| threads | one per physical core (approximated as half the usable CPUs above two), halved when the fp32 weights exceed 60% of free RAM, because every thread keeps its own buffers |
| inter-op threads | always 1: torch's intra-op and inter-op pools multiply into oversubscription |
| attention | `sdpa` when the stack has it, `eager` otherwise; a model that rejects the kwarg is retried without it rather than failed |
| dataloader workers | 0 on Windows/macOS (spawned workers re-import the module), `min(4, cores // 4)` on Linux |
| gradient checkpointing | on when the weights exceed 40% of free RAM: recomputing beats swapping |
| dtype | fp32 unless the weights do not fit, then bf16 — the same `cpu_fp32_weights_fit` rule the loader used, now with one owner |

Every unknown measurement degrades to the conservative answer instead of raising, and the loader logs
the whole plan as one line, so a slow run can be explained instead of guessed at.

## The start path's rules are testable

`routes/training.py` now has `_apply_target_constraints` (the integrated-GPU 4-bit downgrade, out of
the request handler) and `_compute_target_config` (the three keys the worker reads). Both are pinned by
`tests/test_training_start_target.py`: request wins over stored, stored wins over auto, a refused
target is a 400 carrying the registry's own sentence, and the config the worker receives is exactly
what `compute_target_env` reads. The worker enforces the 4-bit rule itself as well, because a config
from a resumed run, the CLI or an older build never passes through the route — and the downgrade is a
warning in the log now, not a quiet info line.

## The UI survives a failed probe

"Run on" was rendered only when the device list arrived, so a failed `GET /api/compute/targets` showed
nothing and the capacity check silently sized the run from whatever the server had stored. The card is
always rendered: a loading line, an error with a **Try again** that bypasses the cache, and — when data
is present but old — a stale-list sentence on the picker rather than a hidden card.

## One capability answer, not two

The registry decided 4-bit with `find_spec` while the loader decides with `ALLOW_BITSANDBYTES` and
`native_kernels_ready`, so a host with an installed-but-dead bitsandbytes was offered a 4-bit path the
loader refuses mid-load. The registry reads the loader's own gate now (the probe is the fallback only
when the library cannot be imported), and `tests/test_device_capability_parity.py` holds the two key
sets and the CPU/GPU/NPU `grad_checkpoint` answers together.

## The polled route is single-flight

The probe cache had a dead `asyncio.Lock`, so two Train pages opening together ran two full probes.
It is a `threading.Lock` with double-checked caching now — `asyncio.to_thread` builds the payload, so an
async lock could never be acquired there — and the TTL, the POST invalidation and the owner gate all
have tests.
