# Release v1.2.3 — refusal messages that name the right vendor

One fix, but it is the kind that matters: after the NPU work made inference vendor-neutral, the
refusals behind it still spoke as if every machine had an AMD part.

| | |
|---|---|
| Version | `1.2.3` |
| Tag | [`v1.2.3`](https://github.com/Goldodemon-Automation/unsloth_X-/releases/tag/v1.2.3) |
| Channel | latest (not a draft, not a prerelease) |

## What was wrong

The inference backend drives Lemonade and FastFlowLM, which only support an AMD XDNA 2 NPU. Its
refusals said so in AMD-only terms:

- A host with no NPU at all was told **"No AMD Ryzen AI NPU was found on this machine"** — which reads
  as a wrong diagnosis on an Intel or Qualcomm machine, and sends the user to check an AMD driver that
  was never involved.
- An Intel NPU that the Studio now reports correctly was told **"this NPU is XDNA 1"**, a generation it
  is not.

## What it says now

| Situation | Message |
| --- | --- |
| No NPU at all | "No NPU was found on this machine." |
| AMD XDNA 1 | "FastFlowLM needs an XDNA 2 NPU (Ryzen AI 300/400 or Ryzen AI Max); this NPU is XDNA 1." |
| Any other vendor | "The NPU runtime (Lemonade and FastFlowLM) can only drive an AMD XDNA 2 NPU (Ryzen AI 300/400 or Ryzen AI Max); this machine's NPU is NPU4." |

The vendor-named message states the runtime's limit instead of asserting something false about the
hardware, which is the difference between a user learning what to install and a user chasing the wrong
driver.

## Limits, stated

- The runtime support itself is unchanged: Lemonade and FastFlowLM drive AMD XDNA 2. A non-AMD NPU is
  reported by the Studio and refused by inference, with the reason.
- Training is untouched by this release.
