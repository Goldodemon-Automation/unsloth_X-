# Release v1.5.0 — the expensive questions get asked once

The previous round made the machine answer faster. This one makes it stop answering twice: four
caches over work that was being re-done on paths a user waits on, a link credential that carries one
right instead of the whole session, an opt-in Host check, a suite that pins the last two rounds' fixes
so a deletion cannot be silent, and an NPU refusal that finally names the hardware you actually own.

## Faster

Four caches, each answering a question that was being re-asked minutes after it was last answered.
Each effect below is the one stated in the module that implements it. None of these rounds produced a
measured before/after timing, and where a number is quoted it is a number of calls, not milliseconds.

**NPU runtime providers — `studio/backend/utils/hardware/npu_providers.py`.** The hardware section
lists six providers on every visit, installed or not, and the answer comes from distribution
metadata, module specs and PATH lookups — nothing is imported, because loading a runtime takes
seconds, can fail on a missing driver, or does not exist at all. The stated cost of one probe is in
the module: *"six PATH walks per call is tens of milliseconds of stat calls that a request path
cannot afford to repeat."* Those rows are now cached for 60 s, so a page load or a status poll inside
the minute pays none of it, and one lock is held across the probe so a burst of concurrent requests
pays for one probe rather than one each. Callers: the NPU matrix (`utils/hardware/npu.py`) and the
training capability planner (`core/training/npu_assist.py`). A runtime installed under a running
server is noticed when the minute expires — no restart.

**Hub model metadata — `studio/backend/utils/hub_metadata_cache.py`.** Before every model load,
`core/training/trainer.py` asks `huggingface_hub.model_info` one question: is this repo gated, and
does it exist for this credential. That call now goes through `model_info_cached`, keyed on
`(repo, revision, scope)` with a 300 s TTL and 256 entries, oldest evicted, with one lock per key so
two threads asking about the same repo collapse onto one fetch while two threads asking about
different repos do not queue behind each other's network call. Effect: one Hub round-trip — and one
charge against the Hub request budget — saved per repeated load of the same `(repo, revision)` under
the same credential. The TTL is short on purpose: gated status stops being true the moment a user
accepts a licence on the Hub, and a long-lived cache would keep refusing a load that is now allowed.
`invalidate(repo)` exists for callers that know the answer changed.

**Dataset and tokenizer fingerprints — `core/training/dataset_fingerprint.py`, over
`utils/stat_signature.py`.** Start hashes every file of the dataset and of the tokenizer, so two runs
can be compared as having trained on the same bytes. On a large local dataset that is seconds of I/O
paid again on every Start, for a digest that only changes when the files do. Two bounded memos now
sit in front of it, 64 entries each, least-recently-used: per-file digests under
`(path, size:mtime_ns)`, whole-tree entry sets under `(root, directory_signature)`. The stated effect, from the
comment describing what they replace: *"a second Start over an untouched dataset costs one stat
walk."* The per-file memo also survives a sibling: rewriting one file of a dataset re-hashes that
file and not the tree around it.

**Hub endpoint probes — `studio/backend/utils/hf_probe.py`.** The other question the Hub paths ask
over and over is whether the configured endpoint answers at all, and it is re-made on a download, a
dataset load and the fit estimate. An unreachable verdict is now remembered for 30 s (`NEGATIVE_TTL_S`),
in a bounded table of at most 64 negatives (`MAX_CACHED_NEGATIVES`) where a read moves the entry to the
back, so the one dropped at the bound is the least recently used; a timeout is remembered for less — 5 s
(`TIMEOUT_TTL_S`) against 30 s, because "a timeout is not a refusal" and a slow mirror written off for the
full window would be declared dead long after it came back. `invalidate_probe_cache()` covers the moment
the network changes under the process, and the clock is injected so the window is testable without waiting
for it. The asymmetry is the whole design, and the module
says why: **a reachable verdict is never cached**, because a stale "reachable" is what sends the next
download at an endpoint that has stopped answering, while a stale "unreachable" only costs a short
delay before it is tried again. This one landed after the round was briefed; it is in the tree and it
is counted in the verification block.

**Route-mount timing — `studio/frontend/src/lib/perf/route-timing.ts`.** Nothing here is faster; this
is the instrument that will say what is. One span per navigation, from the render that starts the new
location to the effect after its content committed, named `route:train` for both `/train` and
`/studio`, folding unrecognised paths into `route:other` instead of minting a span name per URL, and
reported as the slowest three. Wired in `app/routes/__root.tsx` and `features/studio/studio-page.tsx`.
It stays inert until a session opts in (`?perf=1`, the devtools flag, or a build flag) and its entry
list is bounded at 200. **No Train-page mount time is recorded anywhere in this checkout** — the span
exists so a later round can quote one instead of guessing.

## Safer

**Scoped links — `studio/backend/utils/scoped_link.py`, used by `routes/library.py`.** A session
bearer in a `?token=` outlives the click that made it: it lands in shell history, in a proxy's access
log and in the `Referer` of whatever the destination links to, and it carries every right its subject
has. The library download route no longer takes one. It takes `?link=` — two base64url segments,
HMAC-SHA256 over a domain-separated payload, claims `scope`, `sub`, `iat`, `exp`, `nonce` plus the
item id the link names, minted for 300 s. What the code guarantees:

- The signature is checked before the claims are parsed, in constant time, and a token is refused
  whole rather than repaired: strict base64url, a wrong-length signature rejected, the reserved five
  claims refused as payload keys so a payload cannot rewrite its own `exp`.
- `exp` is exclusive, and a link that expires before it was issued is refused.
- Scope and domain are checked on every `verify`, so the download link never opens the library stream
  route and the stream link never opens the download route: separate secrets, separate domains.
- A link that names one item is refused for any other item, and the file is read in the account the
  link was minted in, not in whatever the ambient context can see.
- The secret is `secrets.token_bytes(32)` made at import, so a restart invalidates every link minted
  before it. This is deliberately not a JWT: there is no `alg` to negotiate and nothing to downgrade.

**The scoped link now covers the whole query-string surface — `routes/inference.py`,
`routes/data_recipe/jobs.py`, beside `routes/library.py`.** The library download route was the first, and
the canvas and artifact routes follow the same shape: their own scope (`canvas`), their own secret made at
import, the same 300 s, and a `?token=` answered with a 400 that names `?link=`. The data-recipe export
never reads a session bearer from the query either — its own comment says the link "carries an HMAC
capability rather than the session token, which download history would keep", for thirty minutes — so no
route in this checkout resolves a `?token=` to a subject any
more, and the `?token=` a caller still sees in a served URL is an HMAC media link (the gallery files, the
RAG document, the video clip). What is left is a residue rather than a finding, and it is the one row
`docs/security.md` still carries: `auth/authentication.py:374` keeps the token argument and still resolves
it, so the closure lives in the call sites, and a new route that passes a query token re-opens the whole
finding; no client in this checkout builds such a URL any more, but the routes that would hand out a link
have no minting endpoint yet (see *What is still open*). `tests/test_canvas_link_auth.py` (6 tests) pins
the refusal, the minted link and the wrong-scope case.

**An opt-in Host allow-list — `studio/backend/utils/trusted_hosts.py`, registered in
`studio/backend/main.py`.** DNS rebinding is the shape this closes: a page on `evil.example` rebound to
`127.0.0.1:8888` is same-origin with the backend and can read every unauthenticated `/api` route. Set
`UNSLOTH_TRUSTED_HOSTS` to a comma-separated list of `host[:port]` patterns — a leading `*` matches
subdomains but not the apex, a bare `*` matches everything, a pattern with a port matches only that
port, matching is case-insensitive and ignores a trailing root dot — and any request whose `Host`
matches nothing on the list is refused with a 400 that names the variable. What it does **not** do, in
the module's own words: it is off unless the variable is set, because LAN, tunnel and Colab modes
carry Host values a single list cannot know and "turning a host check on by default would break them
for a smaller gap than it closes". Loopback literals and `localhost` always pass, so an operator
cannot lock themselves out of their own machine. It is pure ASGI rather than `BaseHTTPMiddleware`,
matching the headers middleware, so streaming responses are not wrapped in an anyio stream, and
WebSocket and other non-http scopes pass through untouched. Registered before routing, so a 400 still
gets the security headers from the middleware that wraps it. Two limits are worth naming because they are
easy to read backwards: a request with no `Host` header at all is refused rather than waved through, and
an entry that cannot be parsed is dropped from the list silently — a typo in `UNSLOTH_TRUSTED_HOSTS` makes
that pattern do nothing rather than making the server complain.

**One client-IP resolver — `studio/backend/utils/client_ip.py`, called from `routes/auth.py`.** This is
the item `docs/security.md` used to carry as two disagreeing trust models, and it was worse than a tidying
issue: the login limiter took the **leftmost** `X-Forwarded-For` hop while the shared credential lockout
took the **rightmost**, so behind a proxy that appends, one request was two different clients to the two
throttles — a bucket could be dodged by taking the other path, and an innocent client could be locked out
by a stranger's failures. `routes/auth.py`'s private copy is gone and `_client_ip`, `_bucket_key`,
`_unknown_user_key` and `_desktop_login_key` all key on the shared resolver. Its rule is the **rightmost
untrusted hop**: walk the chain from the proxy end leftwards and take the first address that is not
loopback, link-local, RFC1918 or IPv6 ULA, and fall back to the rightmost hop when every one is internal;
`Forwarded for=` is parsed by the same rules, `CF-Connecting-IP` is honoured only from a loopback peer,
and `UNSLOTH_STUDIO_TRUST_FORWARDED` is still the gate — a direct listener changes nothing, and the rule
only bites where that variable is set. `tests/test_client_ip_agreement.py` (12 tests) requires the same
address from every keying path: direct, single-hop, two-hop, a spoofed `X-Forwarded-For` from a
non-loopback peer, and the tunnel's `CF-Connecting-IP`.

**Regression pins — `studio/backend/tests/test_series_regressions.py` (17 tests).** Each test answers
one question: *if someone deleted the behaviour, would a test fail?* Six blocks, in the file's own
order: the CORS middleware never pairs a wildcard origin with credentials; the preview page ships a
fresh nonce rather than `'unsafe-inline'`; the credential limiter's key table stays bounded and both
`/refresh` and `/change-password` keep recording their outcomes; the training worker keeps refusing
a 4-bit load on an integrated target; the compute route's probe cache keeps its `threading.Lock` and
a POST keeps invalidating it; and `REFUSAL_TOKENS` still covers every refusal token the planner and
the capability probe can emit, which is how a reason stops reaching a user as `snake_case`. Two kinds
of pin are used deliberately: behavioural ones drive the real code, source-level ones read the file
with `ast` where the behaviour cannot be exercised without a GPU, a subprocess or a live server.
Neither kind imports torch, starts a server or touches the network.

**`docs/security.md` is the security record; this file is not a copy of it.** The page states the
threat model, the 30 controls that exist with a `file:line` behind each row, the one item still open with
a note recording the two rows the page cut when this checkout closed them, the greps and the two AST
linters that reproduce the audit, and the suites that pin each control. It is linked from `README.md`,
whose one-line description still says "three open items" — that line is stale by two and is outside what
these notes own, so it wants its own edit before the tag. Read the page itself, not this summary.

## Fewer bugs

Each of these is described by what the user saw, because that is what the fix had to change.

**An Intel or Qualcomm machine was told it had the wrong AMD hardware.** Asking the NPU backend to
load on a machine with a non-AMD NPU raised `No AMD Ryzen AI NPU was found` — a wrong diagnosis, on
a machine with no AMD parts in it, that reads as a prompt to go suspecting an AMD driver. Two
messages were wrong at once: `core/inference/npu_backend.py` answered from an AMD-only PCI probe, so
the refusal could only speak AMD, and the hardware answer carried no `vendor`, so a device the NPU
matrix had found was described as an unsupported XDNA generation. `_require_supported()` now branches
on the vendor the matrix carries: a non-AMD NPU is told that the runtime behind this backend (Lemonade
and FastFlowLM) drives AMD XDNA 2 only, and the machine's family is named. A machine with no NPU at
all is told `No NPU was found on this machine`, with no vendor in it. `tests/test_npu_vendor_inference.py`
(13 tests) pins both halves, including that a matrix with a usable Intel or Qualcomm NPU now reaches
inference instead of being invisible, and that the AMD-only probe keeps the last word only where it is
authoritative.

**The device card was blank on first render.** The "Run on" card decides between a spinner, a failure
and nothing by asking what state the probe is in. `loading` was true only while a request was already
in flight, and the request was started from an effect — so the first render, before any effect had
begun a probe, and any hook mounted inactive, had no error, no data and no `loading`, and
`noticeState()` answered `"none"`. The card simply did not appear, where "Checking which devices this
machine can train on…" belongs. It now reports loading until a first read has been attempted.

**"Try again" erased the error it was answering.** `retry()` cleared the cached failure before starting
its probe, so the message the button was pressed under vanished and was replaced by the same
"Checking…" line the user had just been told to wait out — the documented precedence, a failed read
outranking a retry in flight, was unreachable from the UI. A failure and its button now stay on
screen until the forced probe settles, and only a success clears them. The same path carries a
generation counter, so the older reply a retry bypassed cannot land afterwards and repaint the panel.

**The card kept the device the user had just left.** After a successful pick the POST reply was folded
into the cached payload — and the POST reply carries no `budget` and no NPU capability, both of which
follow the chosen device. Picking the CPU therefore left the discrete GPU's shared-memory sentence
printed under a CPU row until a page reload. A choice now re-reads the whole payload with a forced
probe, which the module's own comment prefers to "inventing the missing fields or leaving the previous
device's sentences on screen", and `retry()` "probes from scratch so a failed read is never the answer
the surface settles on". All three are pinned by name in `studio/frontend/tests/compute-targets.test.ts`:
*a hook with no probe yet reports loading, not a blank card*, *a retry keeps the failure on screen
until its probe settles*, *choosing a target re-reads the payload so budget and npu follow it*.

**The NPU card named a device the picker was not showing.** Two halves, one wrong behaviour. The
backend's `/api/compute/npu/assist` resolved its primary device with a hardcoded `auto` while
`/api/compute/targets` resolved the *stored* choice, so a machine with a stored `cpu` and a discrete
GPU got "The backward pass runs on the discrete GPU" printed directly under a picker reading CPU.
`routes/compute.py` now reads the same stored value `_payload` already reads, through the same
function, falling back the same way on the same error, and
`tests/test_compute_npu_assist_primary.py` (12 tests) requires the two payloads to agree on `resolved`
for one store. On the frontend the answer was cached under a key that left the device out, and that cache
has no clock, so a device switch kept showing the previous device's answer for the rest of the session —
only a changed intent, or the parent's `refresh()` deleting the key, moved it, and neither is something the
user does on purpose. `npuAssistKey`
(`features/npu/npu-training-assist.ts`) now includes the primary device, because it is an input to the
answer — "the same `requested` on a different device is a different answer, not the same one" — and it
is deliberately *not* added to the query string, since the backend reads the device from its own state
and a parameter could only disagree with it. Pinned in `tests/npu-training-assist.test.ts`.

## Consistent UI

The panel family — the NPU setup notice, the NPU training card, the device picker, the capability
card — was written across several rounds, and the older files still carried raw classes. The pass made
them agree, presentation only:

- **One card surface, written as one literal in each file**: `rounded-lg border border-border/60
  bg-muted/50 px-2.5 py-3`, in `features/npu/npu-setup-notice.tsx` and `npu-training-card.tsx`, with
  a shared `focus-visible:ring-2 focus-visible:ring-ring` on every button. Neither file carries a raw
  palette class: `bg-white`/`text-black` appear once between them, in the comment that explains why
  they are not used. `tests/npu-panel-consistency.test.ts` (7 tests) is what keeps the pair from aging
  apart again — same card literal, one border/background treatment, no light-theme assumption, a
  focus-visible ring on every button, one primary-action size, one muted class, one way of announcing
  status text.
- **One status vocabulary**: `role="status"` for the line that says what is happening,
  `role="alert"` plus `bg-destructive/10` for a failure, `text-muted-foreground` for secondary lines,
  and `Button size="sm"` for the one action.
- **The picker follows the interface-font setting** instead of ignoring it: the memory column is
  `max-w-36` on the named scale, which derives from `--spacing`, where a bracketed fixed width stayed
  the same size while the text around it grew. Its focus ring matches
  `PICKER_FOCUS_VISIBLE_CLASS` from `components/resource-picker/picker-focus`, so the offset is the
  background token and the ring holds up in dark mode.
- **The capability card's marks carry the picker rows' icon size and gap** — `size-3.5` in a `gap-1.5`
  cluster — so the two lists on the same screen are the same list, and both take their prose from the
  one function that turns a backend reason token into a sentence (`describeReasons`, in
  `features/compute-targets/types.ts`).
- **A disabled row says why.** A stale list after a failed read keeps its rows visible so the user can
  see what the run was using, with the line "The device list is unavailable; the last known device is
  shown." rather than a set of rows that simply refuse the click.

## Limits, stated

- **Every cache here is bounded, and every one of them ends.** 60 s for the provider rows (one slot,
  keyed on an environment fingerprint), 300 s and 256 entries for model metadata, 30 s for an unreachable
  endpoint probe and 5 s for a timeout with at most 64 negatives, 64 entries each for the dataset and tokenizer memos, 2048
  entries for a tree signature, 200 entries for perf spans. The
  file memos have no clock: they end when a file's `size:mtime_ns` moves. A writer that rewrites a
  file at the same size and the same mtime is invisible to a metadata key — that is the price of not
  re-reading the bytes to decide whether the bytes need re-reading, and model weights and datasets
  are written once.
- **A cached answer is never a different answer.** That is the property each of these four caches was
  designed around, and it is enforced in the same ways: the inputs that could change the answer
  are part of the key (the provider rows are stamped on platform, `PATH`, `PATHEXT`, `QNN_SDK_ROOT`
  and the probe functions themselves, so a stubbed or replaced probe cannot be answered from an older
  cache; the model-metadata key carries a salted hash of the credential and a per-client epoch, so a
  private repo's verdict for one token is never replayed for another; the NPU card's key now carries the
  primary device, for the same reason); a verdict that could be wrong in the dangerous direction is never
  stored (a probe that raised leaves the provider rows uncached, a `fetch` that raises is never
  replayed, a *reachable* endpoint probe is never remembered, a torn or absent read is refused as a key
  — `ABSENT_SIGNATURE` is never a key, `None` is never a
  value, and an `unavailable` fingerprint is never memoized as a hash); and a value is only stored
  under a signature observed both before and after it was derived, so a digest assembled while the
  tree was moving describes no tree that existed and raises instead.
- **NPU training is still impossible.** Nothing in this release changes that, and the caches make the
  statement cheaper, not softer. The runtime pair behind the NPU backend has no backward pass to
  drive, and no provider row in `npu_providers.py` claims one: the capability planner's note is that
  `full` "is unreachable until a provider row claims" a backward-pass token, which is what keeps the
  mode from inflating. NPU is inference and assist. The machine that has an NPU today is a Ryzen AI
  APU whose GPU is integrated and shares the same memory.
- **A link is not a credential.** It is scoped to one route, names one item, dies at `exp`, and must
  never be accepted anywhere that takes a bearer. The surface is covered: `routes/library.py` was first,
  the canvas and artifact routes and the data-recipe export refuse a session bearer too, and no route in
  this checkout resolves one from a query string. The residue is that the auth-layer parameter still exists,
  which is what the one open item in `docs/security.md` says.
- **Route spans measure; they do not optimize.** `?perf=1` is opt-in, and no timing for any page is
  recorded in this checkout.
