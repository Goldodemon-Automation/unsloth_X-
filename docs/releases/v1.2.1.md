## What shipped

### A windowed run history

While a run trains, the history grid is polled every five seconds and every poll replaces the runs
array; a long history re-mounted and re-rendered every card each time. Only not rendering a row
collects that cost — a hidden row still pays its React render — so the grid now renders a first
screen and grows as the reader approaches the frontier.

`src/lib/render-budget.ts` holds the arithmetic as pure functions, so the clamping, the growth and the
layout-skipping policy are pinned by tests instead of drifting one edit at a time:

- `initialWindow(total, firstScreen)` clamps into `[1, total]`. The floor of one is load-bearing:
  growth is driven by the frontier of *mounted* rows, so a window of zero over a non-empty list would
  paint an empty grid that can never grow.
- `nextWindow(rendered, total, step)` only widens, and caps at `total`.
- `contentVisibilityStyle(rendered, index)` keeps rows inside the window `visible` (an on-screen
  `auto` row still pays the bounce) and marks rows past it `auto` with an intrinsic size.
- `historyCardKey(run)` keys on the run's identity, not its index, so a re-sorted list stops
  re-mounting the whole grid on every poll.

Growth is driven by an `IntersectionObserver` on a sentinel after the grid rather than a scroll
listener, because the grid renders through a `display: contents` wrapper and the scroll container
belongs to the page — the observer works against whatever scrolls, fires only near the frontier, and
needs no per-frame handler. The card is now `React.memo`'d with a comparison over the fields it
prints, so an unchanged run cannot re-render when the poll hands back a fresh array. A virtualizer was
the other option and was rejected in a comment: unmounting rows breaks find-in-page, text selection
and anchored dialogs, which is the same reason the chat thread widens instead of recycling.

### Corrections the release-note audit found

Three of these were code, not prose:

- **The capacity check never used the target's budget on a GPU host.** `fit.py` consulted the
  target's own ceiling only when `gpu_memory_gb` was absent, and the wizard always sends it when a GPU
  is reported — so the integrated-GPU path the budget exists for could not run. A named target now
  wins over the page's figure, which stays the fallback for a target this host cannot size.
- **`use-compute-targets` dropped `requested`** from the POST reply, so after picking a device the
  estimate kept sending the target the page had loaded with.
- **4-bit on an integrated GPU was reported and then not enforced.** A request carrying
  `load_in_4bit` would have run the CPU-dequant path the capability report warns about; the start
  route now switches it to 16-bit and says so in the log.
- `torch_missing` — a reason the registry really emits — had no sentence and rendered as the raw
  token in the capability card. The picker also used a hand-set `max-w-[9rem]`, which the UI-scale
  test catches as a width that ignores the interface font size.

And the notes themselves were corrected where they ran ahead of the code: the NPU card offers assist
and off (the route can explain a `full` refusal, the card cannot ask for one), "no other change" now
names the provider table it depends on, the accelerator-class fallback is scoped to Linux and unlisted
AMD ids are not reported at all, runtimes without a version are described that way, the CPU slowness
figure is labelled an estimate, the environment table lists the compile switches an integrated GPU
also receives, and the "smaller of the driver's shared cap" sentence — which matched no code — is
gone.

## Limits, stated

- The window is a mount window, not a virtualizer: rows past it are not in the DOM. A reader who jumps
  to the end of a very long history mounts a page at a time, not all at once.
- An unchanged card no longer re-renders between polls, so its relative-time label ("3h ago") is as
  fresh as the last time the card itself changed. A running run's fields change every poll, so it
  still ticks.
- No speedup is claimed here. `docs/ui-performance.md` is how to attach a number to this change on
  your own hardware.
